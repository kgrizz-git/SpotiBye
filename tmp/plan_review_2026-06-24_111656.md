## Errors

### E1. ESLint `no-restricted-imports` glob fix is half done

The plan's step (line 129) says:

> Update the lint rule override in `src/backend/.eslintrc.json` to cover nested routes by replacing the `routes/*.ts` pattern with `routes/**/*.ts`.

`src/backend/.eslintrc.json:42-55` has two glob fields that need to be updated, not one:

- `files: ["routes/*.ts"]` (line 42) — controls which files the override *applies* to. Change to `["routes/**/*.ts"]` to cover nested files.
- `group: ["../routes/*"]` (line 49) — controls which *imports* are restricted. This is a separate fix.

The half-fix is dangerous: with the new `files` glob but the old `group` pattern, the rule applies to the nested files but does not catch the imports we care about. Concretely, a file at `src/backend/routes/export/jobs.ts` doing `import { analysisRoutes } from '../analysis'` should be blocked. The pattern `../routes/*` matches `import ... from '../routes/foo'` but **not** `import ... from '../analysis'` (one segment above `routes/export/`, not inside `routes/`).

The fix is to broaden the `group` pattern in lockstep with the `files` glob. Options:
- `group: ["../routes/*", "../**/routes/*", "../**/routes/**/*"]` — explicit allow/block list.
- Use a separate override block for the new sub-routes with a stricter group: `["../**/routes/*", "../**/routes/**/*"]`.

Either is fine; the current single-glob change is not. This is the only true correctness gap in the plan.

## Gaps

### G1. `architecture.test.ts` test names will collide once recursion is added

`src/backend/tests/architecture.test.ts:65-77` runs `it()` inside a `for...of` loop with names like `\`${filename} must not import from other routes\``. The function `getFilesInDir` (lines 24-28) is non-recursive and filters with `f.endsWith('.ts')`.

After the plan's step (line 130) — "update to recursively scan directories under `routes/`" — the recursive walk will surface files like:

- `routes/export/index.ts`
- `routes/export/jobs.ts`
- `routes/export/playlist.ts`
- `routes/export/playlists.ts`
- `routes/export/helpers/types.ts`
- `routes/export/helpers/cache-keys.ts`
- `routes/export/helpers/format.ts`
- `routes/export/helpers/errors.ts`
- `routes/export/helpers/file-bytes.ts`

The test name template uses `filename` only (`path.basename(file)`), so two test IDs collide:
- `index.ts must not import from other routes` (sibling route file in the future, plus the new `export/index.ts`)
- `format.ts must not import from other routes` (sibling, plus the new `helpers/format.ts`)

Vitest will throw `Duplicate test name detected` at module load and the whole test file will fail to start. The executor will need to either:
- Switch the test name to a path-prefixed form (e.g. `\`routes/export/jobs.ts must not import from other routes\``), or
- Add the relative path to the test name.

The plan does not mention this. **The new `getAllFilesInDir` (or whatever the executor names it) must emit unique test names.** Recommend the plan call this out explicitly so the executor doesn't discover it the hard way at `npm run test:run` time.

### G2. `buildExportFileKey` type smell not flagged

`src/backend/routes/export.ts:61-66`:

```typescript
function buildExportFileKey(baseKey: string, mode: 'default' | 'rich' | 'lite' | 'csv' = 'default'): string {
  if (mode === 'default') return `${baseKey}:file`;
  return `${baseKey}:file:${mode}`;
}
```

The `mode` union is `'default' | 'rich' | 'lite' | 'csv'`. The first three are XLSX render modes; `'csv'` is a pre-built file format, semantically different. The function is called with `'csv'` at lines 312, 424, 489, but `'csv'` writes to `export:job:<id>:<userId>:file:csv` — a key that never appears in the prebuilt-key fallback order (lines 423-431), so it's write-only. The plan lifts the function as-is into `helpers/cache-keys.ts` without flagging the smell.

Two options:
- Leave it (keep behavior; add a one-line comment in `cache-keys.ts` explaining the legacy `'csv'` slot).
- Split: have `buildExportFileKey(baseKey, mode)` accept only render modes and add a separate `buildExportFileBytesKey(baseKey, kind: 'default' | 'rich' | 'lite' | 'csv')` for the explicit format selector. Bigger churn.

Either is fine; the executor should not "simplify" this to remove `'csv'` without knowing it's a live write target.

## Open Questions

### OQ1. Should the cleanup of `as ContentfulStatusCode` casts and the `newRequestId()` swap be done in the same step as handler extraction?

The plan's step ordering is:
1. Helpers (lines 118-119)
2. Replace `crypto.randomUUID()` (line 121)
3. Unit tests for helpers (line 122)
4. Extract `jobs.ts`, `playlists.ts`, `playlist.ts` (lines 123-125)
5. Compose `index.ts`, reduce facade (lines 126-127)
6. Clean up `as ContentfulStatusCode` (line 128)

Step 2 modifies handlers *in* `routes/export.ts`. Step 4 then moves those handlers (with the new `newRequestId()` calls) into sub-files. The diff will be confusing: the same edit appears twice (once in `routes/export.ts` pre-extraction, once in the sub-file post-extraction).

The cleaner ordering is to interleave the cleanup with the extraction: do helpers + unit tests first, then for each sub-router extraction, also do its handler-level cleanup in the same commit. This makes the per-step diff cohesive and easier to review.

The current ordering is not wrong; it is just a process choice. Flag for the executor to consider, or revise the plan to merge steps 2 and 4.

### OQ2. `newRequestId()` placement in `format.ts` is a stretch

The 105222 review recommended either `format.ts` *or* `request-id.ts`. The plan chose `format.ts`. After the refactor, `helpers/format.ts` will contain seven format-related helpers plus one unrelated request-ID generator. That is a category mix that will confuse the next reader.

Trade-offs:
- Keep in `format.ts` — minimizes new files, but mixes concerns.
- New `helpers/request-id.ts` — adds a 7-line file but keeps `format.ts` pure.
- Skip `newRequestId()` entirely — the `crypto.randomUUID()` calls are not duplicated enough to warrant extraction; the helper saves a single import at each call site.

My recommendation: option 2 (`request-id.ts`). The helper exists, so it should live somewhere coherent. The plan's justification in the banner — "newRequestId moved out of types.ts" — is correct (moving out of `types.ts` was the right direction) but the plan didn't go far enough.

### OQ3. Should the executor confirm the `console.info` count includes only what the plan claims?

The plan's risks section (line 146) says "9 pre-existing `console.info` statements". I re-counted in `routes/export.ts`: lines 315, 535, 542, 593, 676, 722, 809, 838, 850 = **9**. The count is correct.

But the plan ignores the related `console.warn` calls (lines 317, 329, 340, 587, 715, 852 = 6) and `console.error` calls (lines 393, 614, 641, 737, 869, 896, 939, 969, 1016, 1045 = 10). `console.warn`/`console.error` are not strictly forbidden by Golden Principle #5 (which targets `console.log`/`console.info`), so the plan's silence here is fine — but a one-line note in the risks section ("the 16 `console.warn`/`console.error` calls are accepted as out of scope; they are not the same class of violation as `console.info`") would pre-empt the next reviewer's question.

### OQ4. CHANGELOG has multiple `### Changed` blocks under `## [Unreleased]`

`CHANGELOG.md:7-110` has six `### Changed` blocks under `## [Unreleased]`. Adding a seventh is technically fine but the convention is one of each per release. The plan should tell the executor whether to:
- Add to the most recent `### Changed` block (line 93-99), or
- Create a new `### Changed` block.

Recommendation: add to the most recent block. The block-doubling is a pre-existing artifact and the refactor is not the right PR to consolidate.

## Minor Concerns & Improvements

### M1. `crypto.randomUUID()` count in the plan is off by one

The plan (line 121) says "7 call sites" but `routes/export.ts` has **12** `crypto.randomUUID()` calls (lines 180, 196, 227, 513, 523, 550, 655, 673, 751, 775, 944, 1021). Of those:
- 8 are `requestId` declarations (lines 180, 227, 513, 523, 655, 751, 944, 1021) — these *should* use `newRequestId()`.
- 4 are `jobId` declarations (lines 196, 550, 673, 775) — these are *not* request IDs and should stay as `crypto.randomUUID()`.

The plan says 7. The correct number is 8 for `newRequestId()` replacement. The plan should either:
- Correct the count to 8, or
- Be explicit that "the 4 `jobId` calls remain `crypto.randomUUID()`; 8 requestId call sites are replaced with `newRequestId()`".

Either way the executor needs to know which calls are which. A quick table in the plan would prevent accidentally renaming a `jobId`.

### M2. Plan doesn't say what to do with the `batchDataKey` local in `playlists.ts`

`routes/export.ts:776-777`:

```typescript
const batchKey = `export:batch:${jobId}:${userId}`;
const batchDataKey = `${batchKey}:data`;
```

The plan's `buildBatchKey` and `buildBatchDataKey` helpers will replace both. The local `batchDataKey` variable then becomes a single function call. The plan should mention this so the executor knows the locals go away entirely (vs. keeping them as cache for the function call, which would be a needless extra line).

### M3. The `routes/export.ts` facade line count target

The plan says the facade is "≤ 5 lines". With the new `routes/export.ts` reading something like:

```typescript
export { exportRoutes } from './export/index';
```

That is 1 line of real code and 1 trailing newline = effectively 1 line. The "≤ 5" headroom is fine, but the plan should publish the actual 1-line body in the success criteria so the executor doesn't add comments or reformat to "improve" it.

### M4. The `ResumableExportJobStatus` resolution still requires an import

`routes/export.ts:38` currently has:

```typescript
type ResumableExportJobStatus = ReturnType<typeof ExportService.createJobState>;
```

The plan removes this alias (line 56) and says "All route files will directly import and use the standard `ResumableExportJobState` from `services/export`." The new imports are:

```typescript

```

Worth specifying in the plan (or letting the executor infer it) so the type-import surface is auditable. The CHANGELOG entry should mention the rename.

### M5. The plan's "Unit tests cover `cache-keys.ts` and `format.ts`" success criterion is asymmetric

The plan (line 156) lists unit tests for `cache-keys.ts` and `format.ts`. The implementation step (line 122) also lists `errors.ts`. The success criterion should match. Add `errors.ts` to the criterion.

Also, the criterion doesn't include `file-bytes.ts` or `types.ts`. `file-bytes.ts` (the two `generateFileBytes*` functions) is mostly trivial plumbing, so a unit test is optional. `types.ts` is a pure re-export of types, so no test. The current asymmetric coverage is fine but the criterion should be explicit.

### M6. `architecture.test.ts` description is misleading

The plan's step (line 130) says "update `src/backend/tests/architecture.test.ts` to recursively scan directories under `routes/`". This is **adding** coverage, not updating existing tests. The current test does not break — it just doesn't see the nested files. The step description should say "extend with recursive scanning" or "add recursive coverage", not "update". Otherwise the executor may look for a failing test that doesn't exist.

### M7. Step 1 is too vague to action

The plan's first implementation step (line 118) is "Create the `src/backend/routes/export/` directory and helper skeleton." "Helper skeleton" could mean different things — empty files? Files with placeholder headers? A sub-directory plus `index.ts`? A more actionable step would be: "Create `routes/export/index.ts`, `routes/export/jobs.ts`, `routes/export/playlists.ts`, `routes/export/playlist.ts`, and `routes/export/helpers/{types,cache-keys,format,errors,file-bytes}.ts` as empty files, all `export {}` so the import graph compiles before handlers are extracted." That gives the executor a clear first commit and a baseline that `npm run build` accepts.
