## Errors

### E1. E1 from the third review is not fully fixed

The plan's step (line 140) says:

> Update the lint rule override in `src/backend/.eslintrc.json` to cover nested routes by replacing the `routes/*.ts` pattern with `routes/**/*.ts`.

`src/backend/.eslintrc.json:42-55` has two glob fields that need to be updated, not one:

- `files: ["routes/*.ts"]` (line 42) — controls which files the override **applies to**. Change to `["routes/**/*.ts"]` to cover nested files.
- `group: ["../routes/*"]` (line 49) — controls which **imports** are restricted. This is a separate fix.

The half-fix is dangerous: with the new `files` glob but the old `group` pattern, the rule applies to the nested files but does not catch the imports we care about. Concretely, a file at `src/backend/routes/export/jobs.ts` doing `import { analysisRoutes } from '../analysis'` should be blocked. The pattern `../routes/*` matches `import ... from '../routes/foo'` but **not** `import ... from '../analysis'` (one segment above `routes/export/`, not inside `routes/`).

The fix is to broaden the `group` pattern in lockstep with the `files` glob. Options:
- `group: ["../routes/*", "../**/routes/*", "../**/routes/**/*"]` — explicit allow/block list.
- Use a separate override block for the new sub-routes with a stricter group: `["../**/routes/*", "../**/routes/**/*"]`.

Either is fine; the current single-glob change is not. The plan should describe both globs explicitly so the executor updates both.

This is the only true correctness gap remaining.

## Gaps

### G1. Path-imports note in step 2 is wrong

The plan's step (line 132) says:

From `src/backend/routes/export/jobs.ts`:

## Open Questions

### OQ1. Does the plan's Hono sub-app composition preserve middleware ordering?

The plan's `routes/export/index.ts` will:
1. Create a parent Hono app
2. Apply `app.use('*', authMiddleware)` to the parent
3. Mount sub-apps: `app.route('/jobs', jobsApp)`, `app.route('/playlists', playlistsApp)`, `app.route('/playlist', playlistApp)`

In Hono, parent `app.use(...)` middleware runs **before** sub-app middleware. The sub-apps in the plan have no middleware of their own, so `authMiddleware` runs first on every request to `/export/jobs/*`, `/export/playlists/*`, `/export/playlist/*`. This is the same ordering as the current `app.use('*', authMiddleware)` followed by handler registration in `routes/export.ts:176`. So the behavior is preserved.

This is correct, but the plan should explicitly note that sub-apps do NOT call `app.use('*', authMiddleware)` themselves. The current plan implies this (line 45: "applies `authMiddleware` once at the top level") but a careless executor might add it to each sub-app. The success criterion could include "no sub-app file imports `authMiddleware`" as a check.

### OQ2. Will the new `routes/export/index.ts` be visible to existing test mocks?

`tests/export.test.ts:3` imports `exportRoutes` from `../routes/export`, and `:8` mocks `../services/export`, `:164` mocks `../middleware/auth`.

After the refactor:

Vitest's `vi.mock` resolves the path **relative to the file calling `vi.mock`**, not the file being mocked, so `../services/export` from `tests/export.test.ts` still resolves to `src/backend/services/export.ts` and the mock still matches. ✓ (The plan's M2 from the third review correctly notes this.)
- `tests/export.test.ts:164` still mocks `../middleware/auth` — `routes/export/index.ts` will import from `../../middleware/auth` (one level deeper), but again the test file's relative path `../middleware/auth` still resolves to `src/backend/middleware/auth.ts`. ✓

### OQ3. The `buildExportFileKey` mode parameter type smell

`routes/export.ts:61-66` declares:
```typescript
function buildExportFileKey(baseKey: string, mode: 'default' | 'rich' | 'lite' | 'csv' = 'default'): string
```

The mode union mixes two concerns:
- `'default' | 'rich' | 'lite'` — XLSX render modes (meaningful, used in the prebuilt-key fallback chain)
- `'csv'` — pre-built CSV bytes slot (write-only-ish, not in the fallback chain)

A cleaner signature would split these:
```typescript
function buildExportFileKey(baseKey: string, mode: 'default' | 'rich' | 'lite' = 'default'): string
function buildExportFileBytesKey(baseKey: string, kind: 'default' | 'csv' | 'json'): string
```

The third review (G2) raised this; the plan keeps the combined type. Both choices are defensible — the split is a larger refactor that adds a new helper, the combined form preserves call-site stability. The plan should commit to one (the combined form is fine for this PR) and note the type smell as a follow-up, so the next refactor knows it's still pending.

### OQ4. Should `format.ts` and `errors.ts` be one file?

The plan splits helpers into six files: `types`, `cache-keys`, `format`, `errors`, `request-id`, `file-bytes`. Two of them (`format.ts` and `errors.ts`) are small (≤ 60 and ≤ 80 lines respectively per the plan). They could be combined into a single `helpers/format-errors.ts` (or kept separate for SRP).

Both choices are defensible. The plan chooses to keep them separate. This is fine, but `request-id.ts` at ≤ 10 lines is the smallest helper file. If micro-file count is a concern, the three smallest helpers could be combined: `format.ts` + `errors.ts` + `request-id.ts` into a single `helpers/request.ts` (or similar). The plan doesn't need to act on this; flagging for the executor's awareness.
