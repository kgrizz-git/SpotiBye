## Verdict
The plan is structurally sound, evidence-based, and correctly identifies all 36 findings. There are no factual bugs that would block execution, but the plan has accuracy issues, missing test infrastructure references, and two substantive gaps (duplicate plan, stale BL-1 finding). Detailed findings below.

## Findings

### 1. Line numbers in auth.ts have shifted due to critical-high insertions
The critical-high plan's BT-3 (allowlist block at lines 22-35) and BT-4 (4 catch-block console.errors) added ~25 lines to the top of `src/backend/routes/auth.ts`. As a result, the line numbers quoted in BM-1, BM-7, and BL-9 are wrong by ~25 lines.

Actual locations (post critical-high):
- BM-1 `(newTokens as any).refresh_token` cast → `auth.ts:165` (plan says ~143)
- BM-7 generic OAuth error → `auth.ts:141` (plan says ~117-120)
- BL-9 duplicate `token`/`access_token` → `auth.ts:182-186` (plan says ~161-163)

**Action:** The plan should note "lines have shifted; consult the file as marked" or use `rg` patterns instead of line numbers.

### 2. BM-1: Use existing `AuthTokenResponse`, not a new `SpotifyTokenResponse`
The plan says "Define a `SpotifyTokenResponse` interface with the real fields." But `src/backend/types/spotify-api.ts:15-21` already has `AuthTokenResponse` with exactly the right shape:
```ts
export interface AuthTokenResponse {
  access_token: string;
  token_type: string;
  expires_in: number;
  refresh_token?: string;
  scope: string;
}
```

**Action:** Change `refreshAccessToken` return type from `Omit<AuthTokens, 'refresh_token'>` to `AuthTokenResponse`. The `as any` cast at `auth.ts:165` becomes `newTokens.refresh_token`. No new type needed.

### 3. BM-7: The plan's framing is misleading
The plan says "Return the real `error_description` from Spotify (or a mapped error code) to the client in the JSON body." But the OAuth `error_description` from Spotify is already handled at `auth.ts:69-71` (the `?error=...` callback param). The real bug is the **catch block at line 139-142**: it returns a generic "Failed to complete OAuth flow" for any failure (code exchange, profile fetch, KV write, JWT generation), losing all diagnostic context.

**Action:** Reword BM-7 to focus on the catch block. Use the `OAuthFailedError` or similar structured error. Don't conflate with the `error_description` flow.

### 6. BM-8: Incomplete scope
The plan says "wrap `JSON.parse(sessionData)` in try/catch" at `middleware/auth.ts:30`. But `routes/auth.ts:155` (`const session = JSON.parse(sessionData);`) has the **same** unprotected parse in the refresh handler. Both should be hardened, or the plan should explicitly call out only the middleware.

**Action:** Either add a follow-up note for `routes/auth.ts:155`, or expand BM-8 to cover both call sites.

### 7. BL-6: Dead error branches may be reachable
The plan says "Remove the branches for `ValidationError`, `UnauthorizedError`, `NotFoundError`, `RateLimitError` — none are thrown anywhere in the codebase." Confirmed via `rg "throw new (ValidationError|...)"` (none found in `src/backend/`). However, the branches match `err.name === 'ValidationError'` etc. **which CAN be hit by 3rd-party errors with those `.name` properties** (e.g., from `pg`, `mongoose`, `sequelize`).

**Action:** Keep the branches but make them opt-in via a comment explaining the matching is by `err.name` string. Or replace with a single fallback but log a warning when the unknown error is one of these common names. Don't silently delete code that has a real (if rare) function.

### 8. BM-5: Big refactor buried in a "Medium" item
The plan says "Define a `ExportRequestBody` Zod schema (or hand-rolled type guard) for each endpoint and parse with Hono's `c.req.valid('json')` validator. Remove every `body: any` parameter."

This adds a new runtime dependency (Zod) and a significant refactor across `routes/export.ts` (8+ call sites). It's structurally important, but it's larger than a typical "Medium" bug fix and should be:
- Split out as a separate plan, OR
- Scheduled AFTER the refactor-export-ts plan completes, OR
- Done as a "no-Zod" hand-rolled validator pass first (no new dep)

**Action:** Reclassify BM-5 as a separate concern. Add a note: "Defer until `2026-06-21-refactor-export-ts.md` is complete, since the route file shape may change. Add Zod (or hand-rolled type guards) at the new module boundaries."

### 13. FM-5: `health_check` should not return `{"status": "error"}` from `BackendAPIError`
The current code at `backend_client.py:515-519`:
```python
try:
    response = self._make_request("GET", "/health")
    return response
except BackendAPIError:
    return {"status": "unhealthy", "error": "Backend not reachable"}
```

The plan's FM-5 says to catch `Exception`. But `_make_request` already catches `requests.exceptions.*` and re-raises as `BackendAPIError`, so the additional exception types (`JSONDecodeError`, `TypeError`) would only be from a coding bug. The plan's "broader catch" is correct (defense in depth), but the dict return value changes the contract.

**Action:** Confirm the contract: `health_check` returns a dict with at least a `status` key (`"healthy" | "unhealthy" | "error"`). Document in CHANGELOG.

### 15. FM-2: Kivy's `@mainthread` requires the function to be called from a `Clock` schedule, not a thread
The plan says "Decorate `_update_analysis_ui` with `@mainthread`. Confirm the call site is allowed to be async (or wrap with `Clock.schedule_once`)."

`@mainthread` from `kivy.clock` automatically schedules the function on the main thread via `Clock.schedule_once`. It's safe to call from a background thread. The "or wrap with `Clock.schedule_once`" alternative is what you do WITHOUT `@mainthread`; the two are alternatives, not both.

**Action:** Clarify: either use `@mainthread` (auto-schedules), or use `Clock.schedule_once(self._update_analysis_ui, 0)` (manual). The decorator is the simpler path.

**Action:** Reword BL-3: "Extract `isNodeBuffer(x: unknown): boolean` (or just keep the inline check) — `arrayBufferToBase64` is the only consumer of the `typeof Buffer !== 'undefined'` check."

### 18. Missing: explicit test for `parsePlaylistItem` / `parseSpotifyResponse` with malformed items
BM-2 says "After the top-level `parseSpotifyResponse` call, run each entry in `rawData.items` through a `parsePlaylistItem` validator." The current `parseSpotifyResponse` is an `asserts` function that only checks the top-level shape — it doesn't validate items.

**Action:** Either:
- Extend `parseSpotifyResponse` to optionally validate items, OR
- Add a separate `parseSpotifyPlaylistsResponse` (or `parsePlaylistItems`) that includes item-level validation
- Add a unit test for the new validator

The current plan's "use existing `SpotifyPlaylist` type" approach is correct in spirit but vague in implementation. Specify which validator function the implementation should call.

### 19. Missing: BM-10 race-windowing concern
The plan says "Coalesce concurrent refreshes for the same session by storing an in-flight `Promise<TokenSet>` in a module-level `Map`." The plan's test says "fire two refreshes in parallel, assert only one network call to Spotify."

But two callers from the same `sessionId` would only be from a single user's two simultaneous requests. In Cloudflare Workers, each isolate is single-threaded for JS, so the race window is only across awaits. The test should simulate concurrent in-flight requests and verify de-duplication.

**Action:** Be specific about the test setup: use `Promise.all([refresh1, refresh2])` after both have hit the same `Date.now() > session.expires_at` check.

The plan's Verification section says "Update `CHANGELOG.md` with a 'Code quality & hardening' entry covering all 36 findings." This is correct, but with 36 findings, the entry would be long. Consider grouping by category (auth, types, frontend cleanup, etc.) to make the changelog scannable.

**Action:** Group the CHANGELOG entry by category, with one bullet per category referencing the related finding IDs.
