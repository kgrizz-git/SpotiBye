# Plan Review: Refactor routes/export.ts

**Plan:** `docs/exec-plans/active/2026-06-24-refactor-routes-export-ts.md`
**Reviewed:** 2026-06-24

---

## Errors

### 1. Route Path Prefix Duplication (Critical Routing Mismatch)
The plan proposes composing the routing by registering the family sub-apps under prefixes in `src/backend/routes/export/index.ts`:
```typescript
app.route('/jobs', jobsApp);
app.route('/playlists', playlistsApp);
app.route('/playlist', playlistApp);
```
However, in the **Proposed Module Contents** section (lines 107-128), it states that the routes inside each module will still contain their prefixes, for example:
- `jobs.ts` handler definitions: `POST /jobs`, `POST /jobs/:jobId/step`, etc.
- `playlists.ts` handler definitions: `POST /playlists`, `POST /playlists/chunk`, etc.
- `playlist.ts` handler definitions: `POST /playlist/:id`, etc.

If route handlers in the sub-apps retain these prefixes (e.g., `jobsApp.post('/jobs', ...)`), mounting them under their respective prefixes will result in double-prefix routes:
- `/export/jobs/jobs` (instead of `/export/jobs`)
- `/export/jobs/jobs/:jobId/step` (instead of `/export/jobs/:jobId/step`)
- `/export/playlists/playlists` (instead of `/export/playlists`)
- `/export/playlist/playlist/:id` (instead of `/export/playlist/:id`)

**Correction:** The route path registration inside each sub-app file must be relative to the mounted sub-router path. The plan should explicitly specify the following routing declarations:
- **`jobs.ts`**:
  - `POST /` (resolves to `/export/jobs`)
  - `POST /:jobId/step` (resolves to `/export/jobs/:jobId/step`)
  - `GET /:jobId/status` (resolves to `/export/jobs/:jobId/status`)
  - `GET /:jobId/download` (resolves to `/export/jobs/:jobId/download`)
- **`playlists.ts`**:
  - `POST /` (resolves to `/export/playlists`)
  - `POST /chunk` (resolves to `/export/playlists/chunk`)
  - `GET /:jobId/status` (resolves to `/export/playlists/:jobId/status`)
  - `GET /:jobId/download` (resolves to `/export/playlists/:jobId/download`)
- **`playlist.ts`**:
  - `POST /:id` (resolves to `/export/playlist/:id`)
  - `GET /:id/status` (resolves to `/export/playlist/:id/status`)
  - `GET /:id/download` (resolves to `/export/playlist/:id/download`)
  - `DELETE /:id` (resolves to `/export/playlist/:id`)

## Gaps

### 2. Deepening Relative Imports for Sub-App Modules
The plan splits `routes/export.ts` into modules under a new nested directory `src/backend/routes/export/`. 
All imports referencing sibling files in the parent directory (e.g. `../middleware/auth`, `../services/cache`, `../types/env`, `../types/variables`) will break if copied verbatim. Because the files are now one level deeper, the imports must be updated to use `../../` instead of `../`.
The plan should explicitly outline these updated import paths (e.g., `import type { Env } from '../../types/env';`).

### 3. Coupling of Types File to Services Class
The plan proposes placing the `ResumableExportJobStatus` type alias in `helpers/types.ts` as:
`type ResumableExportJobStatus = ReturnType<typeof ExportService.createJobState>;`
This introduces a direct dependency on the `ExportService` class inside the pure types module (`helpers/types.ts`).
**Correction:** Since `services/export-types.ts` already defines and exports `ResumableExportJobState`, `helpers/types.ts` should import that type and export it as an alias:
```typescript
import type { ResumableExportJobState } from '../../../services/export-types';
export type ResumableExportJobStatus = ResumableExportJobState;
```
This keeps the types helper decoupled from the service class logic.

## Minor Concerns & Improvements

### 4. Executable Functions in `types.ts`
The plan recommends placing the `newRequestId()` utility function inside `routes/export/helpers/types.ts`. Mixing executable logic inside a `.ts` file reserved for types/interfaces is a minor anti-pattern. 
**Improvement:** Move the `newRequestId` helper to a separate helper file like `helpers/format.ts` or `helpers/request-id.ts` to keep types clean.

### 5. Inconsistent Cache Key Helper Signatures
For cache key helper functions inside `routes/export/helpers/cache-keys.ts`, the plan proposes adding a sibling `buildBatchFileKey(batchKey)` that takes a pre-composed base key as an argument.
**Improvement:** For complete uniformity and to decouple caller methods from base key formatting, all cache key builders should accept raw identifiers (`jobId` or `playlistId`, and `userId`).
The helper signature list should be structured as follows:
- `buildBatchKey(jobId, userId): string`
- `buildBatchDataKey(jobId, userId): string`
- `buildBatchFileKey(jobId, userId): string`
- `buildSingleExportKey(playlistId, userId): string`
- `buildSingleExportDataKey(playlistId, userId): string`
- `buildSingleExportFileKey(playlistId, userId): string`

### 6. Repetitive Type Casting on `resolveErrorStatus`
Currently, the route handlers cast the return value of `resolveErrorStatus` at all 8+ call sites (e.g., `as ContentfulStatusCode`).
**Improvement:** Update the return signature of `resolveErrorStatus` in `helpers/errors.ts` to return `ContentfulStatusCode` directly:
```typescript
import type { ContentfulStatusCode } from 'hono/utils/http-status';
export function resolveErrorStatus(code: string, message: string): ContentfulStatusCode { ... }
```
This cleans up all call sites and enforces type safety natively.

### 7. Missing Sub-App Typing in Hono Setup
To ensure environment bindings and context variables are correctly resolved without syntax errors or manual assertions in the handlers, the sub-apps must be typed on instantiation.
**Improvement:** Document that each sub-app (`jobsApp`, `playlistsApp`, `playlistApp`) must be explicitly declared with env bindings and context variable types:
`const app = new Hono<{ Bindings: Env; Variables: Variables }>();`
