### G1. The ARCHITECTURE.md table-row text in step 186 has invalid markdown

Step 186 provides the new ARCHITECTURE.md table row inside an inline backtick span:

```
`| `routes/export/index.ts` | Composed Hono sub-app: mounts `jobsApp` at `/jobs`, `playlistsApp` at `/playlists`, `playlistApp` at `/playlist`. Sub-routers live at `routes/export/{jobs,playlists,playlist}.ts`; helpers at `routes/export/helpers/`. Single-playlist export (`POST /export/playlist/:id`), combined export (`POST /export/playlists`), chunked combined export (`POST /export/playlists/chunk`), resumable job API (`POST /export/jobs`, `POST /export/jobs/:jobId/step`, `GET /export/jobs/:jobId/status`, `GET /export/jobs/:jobId/download`), status and download endpoints for each |`
```

The outer backticks form an inline code span. The first inner backtick (`` `routes/export/index.ts` ``) closes the code span, leaving the rest of the line as plain markdown. The line will render as:

`| ` (literal, in code) followed by `` `routes/export/index.ts` `` (inline code) followed by the rest of the line as plain text (which will then try to parse as markdown and may produce unexpected formatting, e.g. `mounts` becoming a list item, `POST` being interpreted as list bullets, etc.).

The fix is to either:
- Use a fenced code block (```) instead of inline backticks
- Strip the inner backticks and use plain text inside the row
- Escape the inner backticks (e.g. use HTML entities or backslash escaping)

Recommended: use a fenced code block:

````
```
| `routes/export/index.ts` | Composed Hono sub-app: mounts `jobsApp` at `/jobs`, `playlistsApp` at `/playlists`, `playlistApp` at `/playlist`. Sub-routers live at `routes/export/{jobs,playlists,playlist}.ts`; helpers at `routes/export/helpers/`. Single-playlist export (`POST /export/playlist/:id`), combined export (`POST /export/playlists`), chunked combined export (`POST /export/playlists/chunk`), resumable job API (`POST /export/jobs`, `POST /export/jobs/:jobId/step`, `GET /export/jobs/:jobId/status`, `GET /export/jobs/:jobId/download`), status and download endpoints for each |
```
````

This is a real rendering issue but not a correctness issue — the executor can still copy the text and fix the formatting when pasting into ARCHITECTURE.md. The plan should be self-consistent, though, so the executor can paste the row verbatim.

### G2. The `precacheJobFiles` parameter list is over-engineered

Step 171 and the helper description (line 125) show the signature as:

```typescript
precacheJobFiles(exportService, cacheService, job, assemblyState, jobKey, buildExportFileKey)
```

Six parameters. The last (`buildExportFileKey`) is a function injected as a dependency, presumably to avoid a circular import.

Checking the dependency graph for the proposed structure:
- `helpers/file-bytes.ts` would import `buildExportFileKey` from `./cache-keys`
- `helpers/cache-keys.ts` does NOT import from `helpers/file-bytes.ts`
- So there is no circular import risk

The dependency injection is unnecessary complexity. The helper could just import `buildExportFileKey` directly:

```typescript
// In helpers/file-bytes.ts
import { buildExportFileKey } from './cache-keys';
import type { ResumableExportAssemblyState, ResumableExportJobState } from '../../services/export-types';

export async function precacheJobFiles(
  exportService: ExportService,
  cacheService: CacheService,
  job: ResumableExportJobState,
  assemblyState: ResumableExportAssemblyState,
  jobKey: string,
): Promise<void> {
  // ... uses buildExportFileKey directly
}
```

Call site:
```typescript
await precacheJobFiles(exportService, cacheService, job, assemblyState, jobKey);
```

5 parameters instead of 6, and the helper is self-contained. The dependency injection version would be:

Call site:
```typescript
await precacheJobFiles(exportService, cacheService, job, assemblyState, jobKey, buildExportFileKey);
```

This adds noise at every call site (only one call site, but still). The dependency injection is a defensive pattern that doesn't pay off here. The plan should either:
- Drop the `buildExportFileKey` parameter and have the helper import it directly
- Document the rationale for the injection (e.g., "this allows `file-bytes.ts` to remain a leaf module with no internal helpers" — but `cache-keys.ts` is internal, not external)

Recommendation: drop the parameter. The helper imports `buildExportFileKey` from `./cache-keys` directly.

## Open Questions

### OQ1. Should the `helpers/cache-keys.ts` `buildExportFileKey` function take raw identifiers or a base key?

The plan's cache-keys.ts description (lines 88-100) lists 10 helper functions. The signatures are:
- Most: `(jobId, userId)` or `(playlistId, userId)` — raw identifiers
- `buildExportFileKey(baseKey, mode)` — takes a pre-composed base key

This is an inconsistency. Most helpers accept raw identifiers and compose the key internally. `buildExportFileKey` takes a pre-composed key and appends `:file[:mode]`. The asymmetry is justified (you need a base key to append `:file` to), but the plan should explicitly say so:

> *Note:* `buildExportFileKey` is the only helper that takes a pre-composed base key. All other helpers accept raw identifiers and compose the key internally. This asymmetry is necessary because the `:file[:mode]` suffix is appended to an already-composed key (e.g., `buildExportJobKey(jobId, userId)`).

Without this note, the executor might try to "fix" the asymmetry by changing `buildExportFileKey` to also accept raw identifiers, which would require knowing the resource type (job vs. playlist vs. batch) — a much larger refactor.

Minor open question. The plan's choice is correct, but the rationale should be explicit.
