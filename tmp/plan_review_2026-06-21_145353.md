# Plan Review: 2026-06-21-bug-fix-critical-high.md

I've reviewed the plan alongside the codebase and the original bug assessment. Overall, the plan covers all 14 findings, but there are a few significant logical errors and gaps in the proposed fixes that will cause bugs or compilation errors if implemented as written.

### 1. **FT-4: Filename Suffix Regex & Logic Error**
The plan proposes using the regex `re.sub(r"_\d+$", "", base)` and doing a filesystem lookup for existing suffixes. This is fundamentally flawed for two reasons:
* **Data destruction:** The regex strips *any* trailing underscore followed by digits. If a user legitimately names their file `My_Playlist_2026.xlsx`, the regex will strip `_2026` and replace it with `_2` (yielding `My_Playlist_2.xlsx`). This corrupts user intent. 
* **Scope creep:** `increment_filename_suffix` is currently a pure string-manipulation function. It doesn't receive a directory path as an argument. Adding a filesystem lookup (`existing = ... # lookup highest existing suffix`) is impossible without changing the function signature and cascading changes across the frontend.
* **Correction:** The function should use regex to parse the suffix, verify if it falls within the expected range (e.g., `_2` to `_4`), and increment it; otherwise, it should safely append `_2` without stripping anything.

### 2. **BT-4: Syntax Error in Catch Blocks**
The plan says to add `console.error('...', err)` inside the catch blocks in `src/backend/routes/auth.ts`. However, the catch blocks in that file currently use the parameterless catch binding syntax (i.e., `catch { ... }`). If a developer follows the plan verbatim without also modifying the catch clause to capture the error (i.e., changing it to `catch (err) { ... }`), it will result in a `ReferenceError` and cause the TypeScript build to fail.

### 3. **BT-7: Unresolved PII Leak (Gap)**
The bug assessment (BE-SEC-2) explicitly flags that storing the `email` field in the KV session is a raw PII violation: *"SessionData.spotify_data: any stores raw PII (email, country) in KV"*. While the plan successfully adds type safety using `Pick<SpotifyUser, 'id' | 'display_name' | 'email'>`, it completely overlooks the data minimization aspect and continues to store the user's email. If the application logic doesn't strictly require the email, it should be omitted from the `Pick` utility type to fully resolve the security finding.
