## Errors

### E1. ESLint `group` pattern fix is structurally incomplete for nested files

The plan's step (lines 143-145) says:

> Update the restricted pattern `group: ["../routes/*"]` to `["../routes/*", "../**/routes/*", "../**/routes/**/*"]` so sibling/nested imports between different route families are blocked.

The new patterns do not catch the case the plan claims they catch. Worked through concretely from `src/backend/routes/export/jobs.ts`:

- `..` resolves to `src/backend/routes/`
- Sibling route file at `src/backend/routes/analysis.ts` is imported as `'../analysis'`

Against the new patterns:
- `'../routes/*'` — `'../analysis'` does not start with `'../routes/'`. **No match.**
- `'../**/routes/*'` — requires a `/routes/` segment in the path. `'../analysis'` has none. **No match.**
- `'../**/routes/**/*'` — same. **No match.**

So an import like `import { analysisRoutes } from '../analysis'` from `routes/export/jobs.ts` is **not** blocked by the new ESLint pattern. The new patterns catch the case where a deeply-nested file (e.g. `src/backend/services/deeply/nested/foo.ts`) imports a route via `../../routes/export/jobs`, but they do not catch the same-directory sibling case the plan claims to address.

The plan's architecture-test update (step 147) is what will catch this:
> resolve import paths relative to the source file. If the resolved absolute path points to a file within `src/backend/routes/` that belongs to a different route family (e.g., `analysis` from `export/`), treat it as a violation.

The architecture test, with path resolution, will catch `../analysis` from `routes/export/jobs.ts`. So the violation will be caught at test time — but **not** at lint time, which is the original purpose of the rule. The plan should either:

1. Use a pattern that actually matches siblings from nested files. Options:
   - `group: ["../analysis", "../auth", "../spotify"]` — explicit list of known sibling routes. Verbose but accurate; requires updating the list when a new route is added.
   - `group: ["../!(index|jobs|playlists|playlist|helpers)/**/*.ts"]` — minimatch negation. May or may not work depending on the minimatch version ESLint bundles.
   - A custom rule or a `path` plugin that does proper resolution.

2. Acknowledge in the prose that the ESLint rule applies to top-level routes only and that nested-route enforcement is delegated to the architecture test. The current prose ("sibling/nested imports between different route families are blocked") implies both are blocked at lint time, which is false.

Recommendation: option 1 with the explicit list, plus a comment in `.eslintrc.json` explaining the maintenance burden. The plan's "Updated pattern" wording is currently misleading.

This is the only true correctness issue remaining. It is a regression from the previous pass's E1 — the pattern update now looks like a fix, but it isn't.

## Gaps

### G1. The architecture test's "different route family" check is not defined

Step 147 says:

> If the resolved absolute path points to a file within `src/backend/routes/` that belongs to a different route family (e.g., `analysis` from `export/`), treat it as a violation.

What defines a "route family"? The plan implicitly defines them by the directory structure:
- Top-level families: `analysis`, `auth`, `spotify`
- Sub-family: `export` (with sub-routers `jobs`, `playlists`, `playlist`)

But the executor needs concrete guidance. Two reasonable interpretations:

1. **Strict (recommended):** A file in `routes/<family>/` may only import from `routes/<family>/**` (same family). All other `routes/<other-family>/*.ts` imports are violations. This means `routes/export/jobs.ts` can import `./playlist` but not `../analysis`.

2. **Loose:** A file in `routes/<family>/` may import any other route file, as long as it's not the parent facade. This means cross-family imports are allowed.

The plan's wording "belongs to a different route family" suggests the strict interpretation. The executor should be told this explicitly. A concrete test logic sketch:

```javascript
function isSameFamily(sourceFile: string, resolvedImport: string): boolean {
  const sourceDir = path.dirname(sourceFile);
  const sourceFamily = sourceDir.split('/routes/')[1]?.split('/')[0] ?? ''; // e.g. 'export' or '' for top-level
  const importDir = path.dirname(resolvedImport);
  const importFamily = importDir.split('/routes/')[1]?.split('/')[0] ?? ''; // e.g. 'analysis' or '' for top-level

  if (sourceFamily === '' && importFamily === '') return true; // both top-level
  if (sourceFamily === '' || importFamily === '') return false; // top-level vs sub-family
  return sourceFamily === importFamily; // both sub-family: same family
}
```

A top-level `routes/analysis.ts` can import `routes/auth.ts` (both top-level) but not `routes/export/jobs.ts` (mixed). A nested `routes/export/jobs.ts` can import `routes/export/playlist.ts` (same family) but not `routes/analysis.ts` (different family).

The plan's success criterion (line 252) says "detects sibling/cross-family route import violations" — this aligns with the strict interpretation. Worth spelling out in step 147.

### OQ2. Will the `routes/export/jobs.ts` placeholder break the `routes/export.ts` re-export?

The implementation step 122 creates `routes/export/index.ts` as `export {};` (a placeholder). Step 142 reduces `routes/export.ts` to `export { exportRoutes } from './export/index';`. The placeholder doesn't export `exportRoutes`, so the import would resolve to `undefined`.

In TypeScript, the re-export of a non-existent named export compiles to JavaScript that re-exports `undefined` at runtime. The Hono app would be `undefined`, and the route would fail at request time with "Cannot read property 'fetch' of undefined" or similar.

The plan says the placeholder files "ensure the project continues to compile" — this is true at the TypeScript level (no compile errors), but the runtime behavior is broken until the placeholder is replaced with real content. The plan's step ordering should ensure that:
- Step 122 creates placeholders for index.ts, jobs.ts, playlists.ts, playlist.ts
- Step 127 creates the helper files
- Step 137-140 extracts handlers into jobs.ts, playlists.ts, playlist.ts
- Step 141 implements routes/export/index.ts (which mounts the sub-apps)

So the actual assembly of the Hono app with real handlers happens at step 141. Between step 122 and step 141, the facade re-exports a non-functional app.

The plan doesn't run `npm run test:run` between these steps (the verification step is at the end, line 153). So the broken state is transient. The plan should note this in the risks section: "between step 122 and step 141, the import chain produces a non-functional Hono app. Do not run `npm run test:run` until step 141 is complete."

Or: the verification step at line 153 should be moved earlier or split into incremental checkpoints. The current plan says "Run full backend verification suite: `npm run test:run && npm run lint && npm run build`" at line 153, which is the last step. This is fine but worth a one-line risk note.
