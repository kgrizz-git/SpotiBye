The plan's self-applied "REVIEWED 2026-06-24 — Ready for execution" banner is mostly justified. The seven items from the previous review are correctly fixed in the new draft (relative paths, sub-routing prefix stripping, `ResumableExportJobStatus` aliasing from `ResumableExportJobState`, uniform `(jobId|playlistId, userId)` key signatures, `ContentfulStatusCode` return type, sub-app `Hono<{Bindings, Variables}>` typing, `newRequestId` moved out of `types.ts`).

What follows is what the second pass found that the first pass did not — there is one critical sizing error, several smaller documentation/process gaps, and a few open questions worth resolving before execution.

## Errors

### E1. `jobs.ts` line budget is impossible against the current handlers

The plan budgets `jobs.ts` at **≤ 250 lines**, but the four handlers allocated to it are already 335 lines of body code before any imports, the sub-app declaration, the typed-Hono scaffolding, or any per-handler error mapping:

| Handler | Lines (current) | Body lines |
|---|---|---|
| `POST /jobs` | 179–223 | 45 |
| `POST /jobs/:jobId/step` | 226–362 | **137** |
| `GET /jobs/:jobId/status` | 365–396 | 32 |
| `GET /jobs/:jobId/download` | 399–519 | 121 |
| **Total handler bodies** | | **335** |

`POST /jobs/:jobId/step` alone (lines 226–362) is the assembly/file-precaching block; it is the densest function in the file and will not compress materially under refactor. A realistic budget is **≤ 380 lines** for `jobs.ts`, and the plan should either:
- Raise the cap and document it (consistent with the explicit ≤ 350 exception already given to `playlists.ts`), or
- Split the resume step into two files (e.g. `jobs/step.ts` and `jobs/download.ts`), or
- Extract the file-precaching block (lines 288–346) into a `precacheJobFiles(...)` helper in `helpers/file-bytes.ts` so the handler itself shrinks.

The success criterion "No file under `routes/export/` exceeds 300 lines (with `playlists.ts` permitted at ≤ 350 lines)" will be violated by `jobs.ts` as written.

## Gaps

### G1. No `CHANGELOG.md` step — violates AGENTS.md Changelog Rule

The active plans convention (`AGENTS.md` → "Changelog Rule") and the precedent set by the completed `2026-06-21-refactor-export-ts.md` plan both require a `## [Unreleased]` → `### Changed` entry in the same PR. The current plan's implementation steps do not include one, and the success criteria do not check for it. The change is user-visible (file structure; re-export facade; renamed `ResumableExportJobStatus` alias) and the rule says:

> Any user-visible change must update `CHANGELOG.md` in the same PR.

Suggested entry (mirroring the wording of the services refactor changelog entry already in the file):
> Refactored `routes/export.ts` (1,050 lines) into a Hono sub-app composition at `routes/export/` with helper modules under `routes/export/helpers/`. The public `exportRoutes` export is preserved; no call-site or test-assertion changes. Type aliases `BatchExportStatus` and `ResumableExportJobStatus` now live in `helpers/types.ts`; `ResumableExportJobStatus` is now an alias of `ResumableExportJobState` rather than `ReturnType<typeof ExportService.createJobState>`.

### G2. `ARCHITECTURE.md` cache-key table is missing the batch and single-export keys

`ARCHITECTURE.md:155-166` documents the backend KV key patterns, but only lists the `export:job:*` keys. The plan's new `buildBatchKey` / `buildSingleExportKey` helpers formalize three additional key families that are currently inlined:

- `export:batch:<jobId>:<userId>` (and `:data`, `:file`)
- `export:<playlistId>:<userId>` (and `:data`, `:file`)

Promoting these to named helpers is a good time to also document them in `ARCHITECTURE.md:155-166`. The table should be updated to include all six keys (or at minimum note that they exist). Otherwise the next agent that looks for a cache key pattern will find it under-documented.

### G3. ESLint `no-restricted-imports` rule does not apply to the new subdirectory files

`.eslintrc.json:42-55` has a rule "Routes must not import from other routes" that uses the glob `routes/*.ts` (non-recursive). The new files at `routes/export/jobs.ts`, `routes/export/playlists.ts`, `routes/export/playlist.ts`, and `routes/export/helpers/*.ts` are **not matched by that glob**, so:

- `routes/export/jobs.ts` could `import` from `routes/analysis.ts` and ESLint would not catch it.
- `routes/export/helpers/format.ts` could `import` from any other route file.

The plan should either:
- Update the glob to `routes/**/*.ts` (and the override to match), or
- Add a separate override for `routes/export/**` with the same pattern, or
- Explicitly state that intra-`routes/export/` imports are allowed but cross-route-directory imports are not, and add a structural test (the `architecture.test.ts` file already exists) to enforce it.

ARCHITECTURE.md:45 enforces "A route file must not import from another route file" as a layer rule, so the lint rule should be made to match.

## Open Questions

### OQ1. Should the `ResumableExportJobStatus` name collision with `services/export-types.ts` be resolved?

`services/export-types.ts:38` already exports `type ResumableExportJobStatus = 'running' | 'assembling' | 'completed' | 'failed'` (a string union). The plan adds a second `ResumableExportJobStatus` in `routes/export/helpers/types.ts` that aliases the full `ResumableExportJobState` (an object interface). Same name, different shape.

Inside the route subtree, the local definition shadows the imported service-layer one, so consumers will see the object interface, which is what `routes/export.ts:38, 241, 370, 407` want. But:
- Anyone reading stack traces from a route handler that throws will see `ResumableExportJobStatus` in the message and may follow the wrong export to understand it.
- If a future test or helper ever imports `ResumableExportJobStatus` from `services/export-types` and uses it where a route expects the object, the type checker will accept it (same name, structurally compatible fields) but a runtime comparison could fail.

Recommended resolutions (pick one):
- Rename the route alias to e.g. `ResumableJobState` or `RouteResumableJob` to avoid the collision.
- Rename the services-layer string union to e.g. `ResumableJobStatusName` to free the name.
- Document the collision in `helpers/types.ts` with a one-line comment explaining the shadowing.

### OQ2. Should `CacheService` key composition be lifted to a typed abstraction (e.g. a `CacheKeys` value object) instead of a flat function library?

The plan extracts 10 cache-key builders into a flat module. An alternative is a single class or factory that returns typed key pairs:

```ts
exportKeys(playlistId, userId)        // { status, data, file }
batchKeys(jobId, userId)              // { status, data, file }
jobKeys(jobId, userId)                // { status, data, assembly, file[mode] }
```

This is more refactor than the plan calls for, but it would be a natural follow-up: handlers stop calling three builders per resource and instead destructure one object. Worth flagging as a follow-up plan rather than expanding this one's scope.

### OQ3. Should the refactor be staged behind a flag or done atomically?

The plan is an atomic all-at-once refactor. Given the 12 route handlers, 1,050 lines, and 4 new helper modules, an atomic commit makes code review harder and a partial revert impossible. Worth considering:
- Step A: extract helpers only (`types.ts`, `cache-keys.ts`, `format.ts`, `errors.ts`, `file-bytes.ts`) with unit tests — verifiable in isolation, behavior-preserving.
- Step B: extract one sub-router (e.g. `playlists.ts` — the smallest at 291 handler lines).
- Step C: extract the remaining two sub-routers.

This is a process question, not a correctness one; the plan is technically fine as a single PR.

### OQ4. `dev-docs/TO_DO.md` is in `dev-docs/`, not in `docs/exec-plans/`

The plan's final step says "Update `dev-docs/TO_DO.md`, move this plan to `docs/exec-plans/completed/`, and update the index." But the new `AGENTS.md` conventions established by the `2026-06-21-repo-organization-guardrails.md` plan (see `docs/exec-plans/completed/`) put TODO lists in a specific location. The current `TO_DO.md` lives at `dev-docs/TO_DO.md:10`, which is the file the plan links. If the TODO is meant to live elsewhere under the new guardrails, the plan should say so. (This may be a pre-existing inconsistency — but if so, the refactor plan is the right place to fix it.)

## Minor Concerns & Improvements

### M1. `routes/export.ts` facade could be the wrong abstraction

The plan keeps `routes/export.ts` as a 1-5 line re-export. The alternatives are:
- Delete `routes/export.ts` and let `routes/export/index.ts` resolve. Importers (`src/backend/index.ts:7`, `tests/export.test.ts:3`) currently write `from './routes/export'`. With `moduleResolution: "bundler"`, TypeScript resolves `./routes/export` to `routes/export.ts` (the file) first, then `routes/export/index.ts` (the directory). Deleting the file would force the second path. The facade is therefore not strictly required for resolution, but it does make the import statement self-documenting ("this is the public surface") and protects against someone later adding a sibling `routes/export-something.ts` that would shadow the directory. Recommend keeping the facade as planned, but the plan should state this rationale so it is not deleted in a future "clean up" pass.

### M2. The "All existing tests pass without modification" claim depends on test-mock path stability

`tests/export.test.ts:8` mocks `../services/export` and `:164` mocks `../middleware/auth`. After the refactor, the new `routes/export/index.ts` will import from `../../middleware/auth` (two levels deep). Vitest's `vi.mock` resolves the path **relative to the file calling `vi.mock`**, not the file being mocked, so the mock still matches the new deeper import path (both resolve to `src/backend/middleware/auth.ts`). This works, but the plan should explicitly call out that the mock paths are **unchanged by design** to make this auditable. As written, a future reader could "fix" the mock path to `../../middleware/auth` and silently lose coverage.

### M3. `parseXlsxRenderMode` return value's tolerance of unknown values

`routes/export.ts:68-74` returns `'auto'` for any input that is not `'rich'` or `'lite'`. This is a soft default. The plan extracts the function to `format.ts` without adding a unit test for the unknown-value case. The `Testing Strategy` section only says "Unit tests are added for `cache-keys.ts` and `format.ts` at a minimum" — that is sufficient, but a single test pinning the `'auto'` default would prevent a future refactor from accidentally tightening the normalization (e.g. throwing on unknown values, which would break the route).

### M4. `batchKey` is reused across `playlists.ts` and `playlist.ts` (different prefixes)

The plan puts `playlists.ts` (batch routes) and `playlist.ts` (single routes) in separate sub-app files. The `buildBatchKey` helper is only used in `playlists.ts`, and `buildSingleExportKey` is only used in `playlist.ts`. That is correct, but the `cache-keys.ts` helper file becomes a flat grab-bag of 10 builders. An alternative: colocate the helpers into the sub-router file that uses them, or split `cache-keys.ts` into `cache-keys-jobs.ts`, `cache-keys-batch.ts`, `cache-keys-single.ts`. The flat form is fine; the plan should not change it. Mentioning this so the next reviewer understands the trade-off.

### M5. `architecture.test.ts` may need a follow-up

`tests/architecture.test.ts` (one of the existing structural tests) likely asserts that `routes/export.ts` exists and is a single-file module. After the refactor, the assertion may need to be relaxed to "exists and re-exports" or extended to "directory `routes/export/` exists with a sub-app composition". The plan does not mention this test, so it may be silently broken or silently updated by the executor. Worth a step.
