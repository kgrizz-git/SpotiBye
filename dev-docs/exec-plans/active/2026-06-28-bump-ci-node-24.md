## TL;DR

- Bump `node-version` from `"20"` to `"24"` in 3 workflow files (6 `actions/setup-node` calls total).
- Add `.nvmrc` with `24` so local development matches CI.
- Bump `@types/node` from `^20.12.0` to `^24.x` in `src/backend/package.json` so `tsc` typechecks against the same Node runtime the workflow will use.
- Add a one-line Node version note to `AGENTS.md` and `CLAUDE.md` so contributors see it without grepping.

- Verify by running `verify-all.sh` and `npm run test:run` under your current local Node, then push and watch CI go green.

## Goal

Bring the CI Node baseline from the past-EOL Node 20 (EOL April 2026) to the current Active LTS Node 24 (EOL April 2028), and make the same version consistent across the CI workflow, the local `.nvmrc`, and the `@types/node` type surface that `tsc` checks against. Zero application code touched, but the dependency version is bumped.

## Background & Rationale

### Why not stay on Node 20

Node 20 entered Maintenance LTS in October 2024 and reached EOL in April 2026. As of June 2026, it is past EOL — no further security patches from the Node release team. Bumping is overdue.

### Why Node 24 and not 22 or 26

- **Node 22** (Maintenance LTS, EOL April 2027) is a safe conservative bump but lands the project on a release that's already in its maintenance window — we'd be doing this again in ~10 months.
- **Node 24** (Active LTS, EOL April 2028) is the current Active LTS. Two years of runway, broadest ecosystem compatibility (Vite, Vitest 4, wrangler 4, all engines-clean), and the right default for a Cloudflare Workers project.
- **Node 26** (current odd-numbered release, EOL ~October 2026) is not LTS. Odd-numbered Node releases get only 8 months of support; jumping to it would mean another bump in 4 months. Worth avoiding for a production-bound project.

### Why this is a separate PR

Per AGENTS.md: "PRs should change one logical thing." The Node bump touches zero application code, so it has the cleanest possible review surface (6 workflow edits + 1 new file + 1 devDep bump + 2 doc one-liners, all single-value changes) and can ship independently. Bundling it with the CI type-error fix would couple two unrelated concerns and make either harder to revert.

### Workflow file audit

All 6 files in `.github/workflows/` were audited. Only 3 need edits:

| File | Uses `setup-node`? | Needs bump? |
|---|---|---|
| `ci.yml` | Yes (line 24) | Yes — `"20"` → `"24"` |
| `deploy-backend.yml` | Yes (lines 39, 75, 105) | Yes — `'20'` → `'24'` × 3 |

| `dependency-review.yml` | No (uses `actions/dependency-review-action` only) | No |
| `security.yml` | No (Python + OSV-Scanner + Bandit, no `setup-node`) | No |

### Why we need `.nvmrc`

Currently nothing in the repo pins the local Node version. The local dev environment can drift from CI silently — and given that the original CI failure was a Node-version-blind class of issue, having the same version locally is a cheap way to prevent future drift. `.nvmrc` is the lowest-friction way to make this enforceable without adding CI steps.

## Risk Assessment

**Low.** The change is config + one devDep bump:
- No application code is touched.
- One devDep version change: `@types/node ^20.12.0` → `@types/node ^24.x` (and a regenerated `package-lock.json`).
- Cloudflare's `workerd` runtime is independent of the CI Node version (workerd ships its own V8).
- The vitest 4 / TypeScript 5.4 / ESLint 8.57 stack is already tested against Node 24 by upstream CI.

**What could still go wrong** (in roughly decreasing likelihood):
1. **The `@types/node` bump surfaces new type errors.** The 20→24 type delta is small (mostly `Buffer`/`Blob`/`Event`/`URL` tightening, plus a few removed deprecated overloads), but a previously-passing call site could start failing. This is the most likely failure mode for this PR. **Mitigated by running `verify-all.sh` immediately after the bump in Step 2**, before any other change.
2. A transitive dep has a tight `engines` constraint that excludes Node 24. Unlikely — none showed up in the existing `package-lock.json` audit. The verification steps in Step 5 will catch this immediately.
3. **`npm ci` under Node 24** ships with npm 10.x. The repo's lockfile is already lockfile v3 (npm 7+ format), so the format is compatible, but there could be subtle resolution differences (overrides handling, hoisting). The full `npm run test:run` run in Step 5 will surface any install-time oddities.
4. The pre-push hooks (especially the new `node-typecheck` hook) hit a Node 24 bash/shell quirk. Unlikely — they're plain shell commands.
5. A test relies on a Node-specific behavior that changed. Lowest probability; none of the 4 new formatZodMessage subtests or the existing chunk/spotify tests do.

If any of these fire, the fix is local: tighten or relax a type, bump a dep, or add a `// @ts-expect-error` / `engines` exemption. None of these are blockers.
