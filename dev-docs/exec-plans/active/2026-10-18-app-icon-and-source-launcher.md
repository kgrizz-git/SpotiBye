# Plan: App Icon at Runtime, README Branding, a Source Launcher, and Public-Repo CI Posture

**Status:** in progress — Phase 2 delivered in #53; Phase 4 delivered in #54; Phases 1, 2b, 3 and 5 not started
**Branch:** plan authored on `feat/app-icon-and-source-launcher` (#52); each phase ships on its own branch
**Created:** 2026-10-18
**Motivation (branding):** The repo ships exactly one icon design (`resources/`) and wires it into the *packaged* app only. Three gaps follow from that: (1) running from source (`python run_frontend_backend.py`) shows Kivy's default icon and an "Untitled"-looking title bar, so the app is unrecognizable in Mission Control/Dock/Alt-Tab; (2) the README — the project's front door on GitHub — has no logo and no badges; (3) a source user has no double-clickable entry point and no branded icon in Finder, which is exactly the "just run it" experience every other desktop app has.
**Motivation (CI posture):** The repo is now **public**, which retroactively invalidates the cost model behind `2026-07-22-reduce-github-actions-billable-minutes.md` (Actions minutes are free for public repos) and leaves three concrete gaps: a stale `push`-trigger + secret-scanning hole in `security.yml`, a stale private-repo justification on SARIF upload in `dependency-review.yml`, and a pre-existing gap where `scripts/tests/` is verified locally but never runs in CI — which directly affects Phase 3's launcher test.

**Ground facts (verified 2026-10-18):**

- Icon assets live in `resources/` only: `SpotiBye black edited 1.png` (1024×1024, square, transparent corners) and `SpotiBye black edited 1-modified.png` (1024×1024, squircle black background). `.icns` (1.8 MB, verified `Mac OS X icon`, type `ic12`) and `.ico` (727 KB) exist for the modified variant only.
- Packaging already consumes the icon: `spotibye.spec:58` (`.ico`, Windows), `spotibye.spec:97` (`.icns`, macOS), `spotibye.spec:99` (`.png`, Linux); `packaging/linux/install-desktop-entry.sh:7` uses the PNG.
- Nothing sets a runtime window icon: `rg -i icon src/frontend -g '*.py'` matches only `UIConstants` (unrelated). Window setup lives in `set_window_basics()` — `src/frontend/utils/platform_utils.py:366-390` — called from `BackendSpotifyExporterApp.build()` at `src/frontend/app/backend_app.py:134`. The failure path `_fallback_window_setup()` (`platform_utils.py:417-428`) sets title/size only.
- Kivy is 2.3.1. The SDL2 provider reads `self.icon or Config.get('kivy', 'window_icon')` only once, on first window creation (`.venv/.../kivy/core/window/window_sdl2.py:365-385`). That happens when `kivy.core.window` is first imported, which is before `build()`. `Window.icon` is a plain `StringProperty` with no `on_icon` observer (`kivy/core/window/__init__.py:401`), so **assigning `Window.icon` after creation is a no-op**. The calls that work post-creation are `Window.set_icon(path)`, which the SDL2 override sends straight to `SDL_SetWindowIcon` (`window_sdl2.py:456-457`), and the idiomatic `App.icon`: `App._run_prepare` calls `window.set_icon(self.get_application_icon())` right after `build()` returns (`kivy/app.py:941-943`), and `App.on_icon` re-applies it on change (`:1212-1214`). Kivy's own default is `kivy-icon-64.png` on Windows / `kivy-icon-512.png` on macOS (`window_sdl2.py:376-384`), which confirms PNG is accepted on every desktop platform.
- The same post-`build()` hook calls `window.set_title(self.get_application_name())` (`kivy/app.py:940`). `BackendSpotifyExporterApp` never sets `App.title`, so Kivy overwrites the title from `set_window_basics()` with the class-derived `BackendSpotifyExporter`. This is the real cause of the odd title bar in the Motivation.
- The PyInstaller entry point is `run_frontend_backend.py` (`spotibye.spec:114`), so the launcher must drive that same file, not a second entry.
- macOS per-file custom icons: `/usr/bin/SetFile` exists here (Xcode CLT at `/Applications/Xcode.app`). `SetFile -a C` exited 0 and changed `com.apple.FinderInfo`, but **no `com.apple.ResourceFork` xattr appeared**. That is expected: `-a C` only sets the "has custom icon" Finder flag and copies no icon data, so the `<icns>` argument does not attach an icon at all. Finder rendering was never visually confirmed, and this environment has no `AppKit` (pyobjc). A flag with no icon payload is the likely result, not a branded file. `SetFile` also requires Xcode Command Line Tools, which a stock user Mac does not have.
- No `.gitattributes` in the repo, so a committed `.command` file must be LF-only and mode `100755` or bash will reject it.
- There is no test module for `platform_utils` today (`ls src/frontend/tests | rg -i platform` → no match).
- `dev-docs/guides/frontend-distribution-guide.md:25-28` documents the icons as `src/frontend/assets/icon.{ico,icns,png}` — a path that does not exist. Stale; fix it while here.
- README has no image and no badges. Workflow names for badges: `CI` (`ci.yml`), `Build Executables` (`build.yml`), `Security Scan` (`security.yml`), `OSV PR Scan` (`dependency-review.yml`). Triggers matter: `ci.yml` runs on push **and** PR to `main`/`develop`/`WIP` with no path filter, whereas `security.yml` and `dependency-review.yml` are **PR-only with path filters** — a status badge for either reports "skipped" or stale most of the time and is misleading.
- Repo guardrails that constrain this plan: `scripts/check-repo-structure.sh:59-71` requires active plans to use `- [ ]` tracking (a hard error). `scripts/check_docs_hygiene.py` checks that the plan is indexed in `active/README.md` and has a `TO_DO.md` backlink, but it only warns: `main()` always returns 0 (`:159-169`). Docs are capped at 300 lines by the file-length hook, hence tight phases.

**Public-repo ground facts (verified 2026-10-18 via `gh api`):**

- `gh repo view --json visibility` → `PUBLIC`, `isPrivate: false`. GitHub-hosted Actions minutes are therefore free; that includes the `windows-latest`/`macos-latest` matrix in `build.yml:74-75`, so the billable-minutes optimization target no longer exists.
- **Code Scanning is already enabled and running** — 4 CodeQL alerts on `refs/heads/main` (2 fixed, 2 dismissed as false positives). There is **no `codeql.yml`** in `.github/workflows/`, so this is GitHub's automatic default setup for public repos. Do **not** add a CodeQL workflow: it would duplicate analysis and can conflict with the default setup.
- **Dependabot alerts: 3 open** (free on public repos). Secret scanning endpoint responds (0 alerts).
- **Branch protection is now unblocked**: `gh api repos/kgrizz-git/SpotiBye/branches/main/protection` returns `404 Branch not protected`, where the billable-minutes plan recorded a `403 "Upgrade to GitHub Pro or make this repository public to enable this feature"` (`:126`). The tier blocker is gone; the feature is simply unconfigured.
- `security.yml` **already scans `main`** via `schedule: cron '0 0 * * 1'` (`:25-26`) plus `workflow_dispatch` (`:27`); most recent schedule run 2026-10-19 00:00 UTC, `success`. The gap is immediacy on merge, not coverage.
- **The `push` trap:** adding `push: branches: [main]` to `security.yml` as written would skip *both* TruffleHog steps. The PR-diff step is gated on `github.event_name == 'pull_request'` (`:56`) and the full-history step on `schedule`/`workflow_dispatch` (`:69`). A push-to-main run would report `TruffleHog | skipped` in the step summary while looking green: zero secret scanning on merges.
- **The second `push` trap:** the PR-diff step diffs `base: ${{ github.event.repository.default_branch }}` against `head: HEAD` (`:60-61`). On a push to `main` both resolve to `main`, so merely widening its `if:` yields an empty diff (or a same-commit error) and still scans nothing. A push run needs `base: ${{ github.event.before }}`, or it must use the full-history step.
- `security.yml` uses `concurrency: cancel-in-progress: true` keyed on `github.ref` (`:34-36`). Two quick merges to `main` would cancel the first scan, leaving that merge unscanned.
- `dependency-review.yml` is **not** `actions/dependency-review-action`; it calls OSV's PR-diff reusable workflow, chosen *because* of the old private status (`:27-29`). Its contract is a base↔head diff, so a `push` trigger is semantically meaningless. `merge_group` (`:14-15`) is **inert today**: it fires only for a merge queue, and a merge queue needs branch protection or a ruleset, which `main` does not have (see the `404` above). It also runs *before* code lands, not after. Nothing currently re-scans dependencies once code reaches `main`. The weekly `security.yml` OSV step (`:114-130`) is the actual backstop.
- `dependency-review.yml:36` sets `upload-sarif: false` with the rationale (`:34-35`) "private personal repos do not have GitHub Code Scanning enabled". Code Scanning is now live, so that justification is dead.
- **CI never runs `scripts/tests/`**: the frontend job's only test step is `pytest src/frontend/tests/ -v` (`.github/workflows/ci.yml:81`), while `scripts/verify-frontend.sh:26` runs `scripts/tests/` locally only (67 tests, all passing on 2026-10-18). This is pre-existing (the setup-selfhost tests are in the same boat) and means Phase 3's launcher test would be dead weight in CI unless the job is extended.
- CI badge viability is therefore phase-dependent: `ci.yml` runs on push **and** PR with no path filter (always-valid badge), `security.yml`/`dependency-review.yml` are PR-only with path filters (misleading badge) — and Phase 4 changes that for `security.yml` if it lands.

## Phase 3 — Double-clickable launcher with first-run icon association

- [x] Add `SpotiBye.command` at the repo root, committed with LF endings and mode `100755` (`git update-index --chmod=+x`); add a `.gitattributes` rule (`*.command text eol=lf`) so line endings survive Windows checkouts with `core.autocrlf`. The executable bit is carried by the git index mode, not by `.gitattributes`. Confirm with `git ls-files -s SpotiBye.command` (expect `100755`) and `file SpotiBye.command`.
- [x] Launcher body: `cd "$(dirname "$0")"` first — Finder opens Terminal with `$HOME` as cwd, not the script's directory, which is the classic double-click bug; then prefer `.venv/bin/python`, fall back to `python3` only if it can `import kivy`. Otherwise print an explicit "run `python3 -m venv .venv && .venv/bin/python -m pip install -r requirements.txt`" (use the venv's own pip, so packages land in the interpreter the launcher picks) message and exit non-zero. A bare `python3` without deps would otherwise die in an `ImportError` with no hint. then `exec "$PY" run_frontend_backend.py` so signals and the exit code pass through and the app is the last process.
- [x] First-run icon association, run **once** and never allowed to block the launch:
  - [x] Guard: skip when `SpotiBye.command` already has a `com.apple.ResourceFork` xattr (`/usr/bin/xattr -p com.apple.ResourceFork`, stock on macOS). Do **not** key on the FinderInfo custom-icon flag alone: `SetFile -a C` sets that flag with no icon data, which would make a failed attempt look done and suppress every retry. Use a gitignored sentinel only as a "tried and failed, don't nag" marker, and add it to `.gitignore`.
  - [x] Mechanism ladder, first one that succeeds wins: (1) `osascript -l JavaScript` that runs `ObjC.import('AppKit')`, loads the `-modified.icns` with `$.NSImage.alloc.initWithContentsOfFile(...)`, and passes it to `$.NSWorkspace.sharedWorkspace.setIconForFileOptions(image, file, 0)`. This is stock macOS, needs no Xcode CLT, scripts no other app (so no Automation prompt is expected), and returns a boolean that reports success. (2) Give up with a one-line hint naming the failure. `SetFile -a C` is **not** a rung: it sets the flag but attaches no icon. The CLT-only `DeRez`/`Rez -append` resource-fork recipe is the only toolchain alternative; skip it unless rung (1) fails in the manual check. Quote the `resources/SpotiBye black edited 1-modified.icns` path, because it contains spaces.
  - [x] Every branch is `|| true`-style: a failed icon must never stop the app from starting, and the message must name the failure so a user can act.
- [x] Scope: macOS gets the launcher. Other platforms get a short "run `python3 run_frontend_backend.py`" line and no icon work — Windows Explorer cannot set per-file icons from a script, and inventing `.bat`/`.desktop` variants here is scope creep (see Out of scope).
- [x] Phase 1 and Phase 3 compose deliberately: the launcher brands the Finder file, and the app now brands its own window, so a source run looks branded at both layers without touching packaging.
- [x] Test: add a Python test under `scripts/tests/` asserting `SpotiBye.command` exists, is LF-only, is executable, drives `run_frontend_backend.py`, and that the icon block is guarded by the already-set check. (Shell-level behavior is verified manually, not in CI: the `frontend` CI job runs on `ubuntu-latest` only, `ci.yml:50`.)
