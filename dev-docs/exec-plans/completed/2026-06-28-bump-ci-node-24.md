# Bump CI Node Version from 20 to 24 LTS

> **Linked from:** [TO_DO.md "Verify release build pipeline"](../../backlog/TO_DO.md)
>
> **For agentic workers:** Steps use checkbox (`- [ ]`) syntax for tracking. Mark steps complete (`- [x]`) as work is finished.

## TL;DR

- Replace `node-version: "20"` with `node-version-file: ".nvmrc"` in 6 `actions/setup-node` calls across 3 workflow files — this makes `.nvmrc` the single source of truth (no version string duplicated between workflows and the file).
- Add `.nvmrc` with `24` so local development matches CI **and** so the lockfile generated in the next step is produced by the same npm major CI uses.
- Bump `@types/node` from `^20.12.0` to `^24.x` in `src/backend/package.json` (run `npm install` under Node 24 / npm 10 to keep the lockfile in lockstep with CI's npm 10).
- Add a one-line Node version note to `AGENTS.md` and `CLAUDE.md` so contributors see it without grepping.
- **Total scope:** 6 workflow edits + 1 new file (`.nvmrc`) + 1 dep-version bump in `src/backend/package.json` (and `package-lock.json` regenerates) + 2 doc edits (one line each in `AGENTS.md` and `CLAUDE.md`).
- Verify with `actionlint`, `verify-all.sh`, and `npm run test:run`, then push and watch CI go green.
- **Why Node 24 specifically:** Node 20 is past EOL (Apr 2026). Node 22 is in maintenance already. Node 24 is the current Active LTS (EOL Apr 2028) — broadest ecosystem compatibility and 2 years of runway. Node 26 is even-numbered (so it *will* be LTS) but as of today it's still in the 8-month current-release window, not yet Active LTS. Revisit Node 26 in a follow-up once it's been Active LTS long enough.

## Goal

Bring the CI Node baseline from the past-EOL Node 20 (EOL April 2026) to the current Active LTS Node 24 (EOL April 2028), and make `.nvmrc` the **single source of truth** for that version (read by both nvm/fnm locally *and* `actions/setup-node` in CI via `node-version-file: '.nvmrc'`). Also bump `@types/node` to keep the type surface in lockstep. Zero application code touched, but the dependency version is bumped and `.nvmrc` is added.

### Step 3 — Bump `@types/node` in `src/backend/package.json`

CI will run on Node 24, but `tsc` checks against `@types/node`. Leaving them out of sync is exactly the kind of version drift this PR is meant to prevent (and would create a window where `tsc --noEmit` passes locally on the old types but fails in CI if the new types tighten any signature we touch).

**This step must be run under Node 24** so the generated `package-lock.json` is produced by the same npm major version CI will use to consume it. Node 24 ships npm 10; Node 26 ships npm 11. Running `npm install` under Node 26 would generate a lockfile with npm 11 metadata that `npm ci` under npm 10 in CI could handle inconsistently (different hoisting decisions, stricter peer-dep metadata). Practical impact is small for most projects but the cost of doing it right is also small — just `nvm use 24` first.

**Nuance worth knowing:** `src/backend/tsconfig.json` has `"types": ["@cloudflare/workers-types"]`, which scopes global `@types/*` loading to just that one package. The practical effect is:
- `tsc --noEmit` over **app source** does **not** load `@types/node` — it only sees `@cloudflare/workers-types` globals. So the main app's type surface won't shift as a result of this bump.
- The Vitest **typecheck** (the new one we added in the previous plan) **does** load `@types/node` for test files (Vitest picks up the standard Node environment by default). So new type errors from the bump are most likely to surface in `tests/**/*.test.ts`, not `src/**/*.ts`.

- [x] **Switch to Node 24:** `nvm use 24` (or `fnm use 24`). If Node 24 isn't installed yet, `nvm install 24` first. Confirm with `node --version` → `v24.x`. (On this dev box, no nvm was installed — `brew install node@24` was used, then `PATH="/opt/homebrew/opt/node@24/bin:$PATH" npm install ...` invoked Node 24 directly.)
- [x] **Edit `src/backend/package.json`** — change `"@types/node": "^20.12.0"` to `"@types/node": "^24.0.0"` (or the latest 24.x; pick the same major the CI now runs).
- [x] **Run `npm install` in `src/backend`** to regenerate `src/backend/package-lock.json` with the new resolution (under Node 24 / npm 10).
- [x] **Run `./scripts/verify-all.sh`** immediately after — bumping `@types/node` can surface new type errors in test files (per the nuance above). If any appear, fix them in this same PR (they should be small; the test code doesn't lean on Node-specific globals heavily).
- [x] **Run `cd src/backend && npm run test:run`** in addition — this runs the Vitest typecheck on tests, which is the path where the new types actually load. Confirms no test-file regressions.
- [x] **Run `cd src/backend && npm audit`** as a defensive check — confirms the `@types/node` bump didn't pull in a vulnerable transitive. Should be a no-op for a dev-only dep but cheap to verify.

## Risk Assessment

**Low.** The change is config + one devDep bump:
- No application code is touched.
- Workflow edits are now `node-version: "20"` → `node-version-file: ".nvmrc"` (rather than hardcoding `"24"`) — strictly smaller blast radius: the literal version lives in one place.
- One devDep version change: `@types/node ^20.12.0` → `@types/node ^24.x` (and a regenerated `package-lock.json`).
- Cloudflare's `workerd` runtime is independent of the CI Node version (workerd ships its own V8).
- The vitest 4 / TypeScript 5.4 / ESLint 8.57 stack is already tested against Node 24 by upstream CI.

**What could still go wrong** (in roughly decreasing likelihood):
1. **The `@types/node` bump surfaces new type errors in test files.** Per the `tsconfig.json` `"types": ["@cloudflare/workers-types"]` scoping, the new types load into Vitest's test typecheck but not the app's `tsc --noEmit`. So the most likely failure surface is `tests/**/*.test.ts` (the `node-test`, `node:assert`, `node:crypto`, `node:url` etc. imports, plus the few tests that touch Node globals). **Mitigated by running `verify-all.sh` *and* `npm run test:run` immediately after the bump in Step 3** — `test:run` is the one that exercises the Vitest typecheck.
2. A transitive dep has a tight `engines` constraint that excludes Node 24. Unlikely — none showed up in the existing `package-lock.json` audit. The verification steps in Step 5 will catch this immediately.
3. The pre-push hooks (especially the new `node-typecheck` hook) hit a Node 24 bash/shell quirk. Unlikely — they're plain shell commands.
4. A test relies on a Node-specific behavior that changed. Lowest probability; none of the 4 new formatZodMessage subtests or the existing chunk/spotify tests do.

**Pre-existing issue (not caused by this PR, but worth flagging during the bump):**
- `.pre-commit-config.yaml` pins `@typescript-eslint/eslint-plugin@6.0.0` and `@typescript-eslint/parser@6.0.0` in the `eslint` hook's `additional_dependencies`, while `src/backend/package.json` declares both at `^8.61.0`. The local pre-commit hook therefore uses typescript-eslint v6 while `npm run lint` and CI use v8. A rule that v6 accepts but v8 rejects (or vice versa) could cause a local pre-commit pass to fail in CI, or vice versa. **Not fixed in this PR** — see the Pre-Merge Housekeeping item that adds a follow-up TODO.

If any of these fire, the fix is local: tighten or relax a type, bump a dep, or add a `// @ts-expect-error` / `engines` exemption. None of these are blockers.
